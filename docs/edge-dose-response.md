# Appendix J edge-dose-response reproduction

This workflow reproduces the six-model by five-dataset edge-perturbation
panels for the `erm`, `last`, `head`, and `full` checkpoint preparations. MLP
is excluded because it does not use graph edges.

Each non-zero dose contains five independently generated graph pairs: a
homophily-directed treatment and a random degree-preserving control. The dose
grid is 0%, 5%, ..., 100% for PubMed, ogbn-arxiv, Amazon-ratings, and
arxiv-year. Roman-empire ends at 70% because the fixed generator cannot
construct all five registered graph pairs above that dose.

Each model-dataset cell uses 30 registered checkpoints. The `last`, `head`,
and `full` panels evaluate all six graph models on all five datasets. The ERM
panel evaluates 24 cells here and combines them with the six previously
generated GCN and GraphSAGE-mean summaries for PubMed, ogbn-arxiv, and
arxiv-year.

Raw datasets, checkpoints, graph arrays, and checkpoint-level predictions are
intentionally excluded from Git. They are written below ignored run
directories. Git contains the portable code, registered manifests,
environment specifications, compact summaries, and paper figures.
Machine-specific scheduler files and operational state must remain outside
the repository.

## Resource requirements

Run the commands from a clean clone of this repository. Build the environment
described by `environment.yml` before collecting results.

```bash
conda env create -f environment.yml
conda activate hfd-repro
python -m pip install -e .
```

Graph generation and analysis can run on CPU. Training and evaluation use
PyTorch GPU execution. Each `evaluate` invocation expects one visible GPU.
The large-dataset H2GCN evaluations require at least 40 GiB of GPU memory.

Submit resource-heavy commands through the scheduler available at the
execution site. The repository deliberately does not prescribe
machine-specific submission commands. Independent model-dataset cells may
run concurrently, but two processes must not write the same checkpoint
shard.

Actual collection requires a clean committed worktree. The runner records the
experiment revision, implementation revision, input hashes, checkpoint
identities, graph identities, and output hashes.

## Relative run roots

The examples below use only paths relative to the repository root.

```bash
DATA_ROOT=artifacts/data
ARRAY_ROOT=artifacts/manifests
MANIFEST_ROOT=manifests/datasets
CHECKPOINT_ROOT=artifacts/runs

GRAPH_ROOT=artifacts/edge-dose-response/graphs
CATALOG_ROOT=artifacts/edge-dose-response/catalogs
SMOKE_ROOT=artifacts/edge-dose-response/smoke
LEGACY_ROOT=artifacts/edge-dose-response/legacy
```

The graph catalogs contain dataset-relative paths, byte counts, and SHA256
hashes. An authenticated graph directory can therefore be moved without
changing its identity.

## Prepare datasets and checkpoints

Download and reconstruct the registered datasets and splits:

```bash
python scripts/download_datasets.py
```

The following command trains the four preparations for the six graph models.
It is resumable. Use the dataset, model, preparation, split, and seed filters
exposed by `scripts/train_models.py` to divide the work into independent
scheduler tasks if required.

```bash
python scripts/train_models.py \
  --main-only \
  --device cuda \
  --model gcn \
  --model graphsage-mean \
  --model acm-gcn \
  --model gpr-gnn \
  --model h2gcn \
  --model linkx \
  --preparation erm \
  --preparation last \
  --preparation head \
  --preparation full
```

A complete checkpoint store contains 30 runs for every requested model,
dataset, and preparation. Each run must contain `checkpoint.pt`,
`config.json`, and `run_data.npz`. The `last` and `head` configurations must
identify the corresponding ERM run through `parent_run_id`; `full` has no
parent. See `docs/raw-result-store.md` for the complete raw-run contract.

Existing checkpoint stores can be reused by setting `CHECKPOINT_ROOT` to
their relative location.

## Evaluate the four preparations

Each actual invocation evaluates all 30 checkpoints for one model-dataset
cell and writes one atomic resumable shard per checkpoint.

```bash
evaluate_cell () {
  preparation="$1"
  dataset="$2"
  model="$3"

  if [ "$preparation" = erm ]; then
    output_root="outputs/edge-dose-response-expansion/actual"
  else
    output_root="outputs/edge-dose-response-recovery/actual/$preparation"
  fi

  python scripts/run_edge_dose_response_expansion.py evaluate \
    --phase actual \
    --preparation "$preparation" \
    --dataset "$dataset" \
    --model "$model" \
    --graph-root "$GRAPH_ROOT" \
    --catalog-root "$CATALOG_ROOT" \
    --checkpoint-root "$CHECKPOINT_ROOT" \
    --output-root "$output_root" \
    --data-root "$DATA_ROOT" \
    --array-root "$ARRAY_ROOT" \
    --manifest-root "$MANIFEST_ROOT" \
    --device cuda
}
```

The ERM expansion contains four models on PubMed, ogbn-arxiv, and arxiv-year,
and all six models on Roman-empire and Amazon-ratings:

```bash
for dataset in pubmed ogbn-arxiv arxiv-year; do
  for model in acm-gcn gpr-gnn h2gcn linkx; do
    evaluate_cell erm "$dataset" "$model"
  done
done

for dataset in roman-empire amazon-ratings; do
  for model in gcn graphsage-mean acm-gcn gpr-gnn h2gcn linkx; do
    evaluate_cell erm "$dataset" "$model"
  done
done
```

Each recovery preparation directly evaluates the complete 30-cell matrix:

```bash
for preparation in last head full; do
  for dataset in pubmed ogbn-arxiv roman-empire amazon-ratings arxiv-year; do
    for model in gcn graphsage-mean acm-gcn gpr-gnn h2gcn linkx; do
      evaluate_cell "$preparation" "$dataset" "$model"
    done
  done
done
```

The calls above may be divided into independent scheduler tasks. Completed
shards are authenticated and skipped when a cell resumes. Use separate output
roots for the four preparations; they share only the graph root and catalogs.

## Validate the raw panels

Validate each preparation after every required model-dataset cell has
completed:

```bash
for preparation in erm last head full; do
  if [ "$preparation" = erm ]; then
    output_root="outputs/edge-dose-response-expansion/actual"
  else
    output_root="outputs/edge-dose-response-recovery/actual/$preparation"
  fi
  python scripts/run_edge_dose_response_expansion.py validate \
    --preparation "$preparation" \
    --graph-root "$GRAPH_ROOT" \
    --catalog-root "$CATALOG_ROOT" \
    --checkpoint-root "$CHECKPOINT_ROOT" \
    --output-root "$output_root"
done
```

Validation writes `baseline_rows.jsonl`, `paired_rows.jsonl`, and
`validation.json` below each preparation's `final/` directory.

Expected counts are:

| Preparation | Checkpoint shards | Baselines | Paired rows |
|---|---:|---:|---:|
| ERM expansion | 720 | 720 | 66,600 |
| `last` | 900 | 900 | 84,600 |
| `head` | 900 | 900 | 84,600 |
| `full` | 900 | 900 | 84,600 |

Across the three recovery preparations, this is 2,700 checkpoint shards,
2,700 baselines, and 253,800 paired rows.

Validation also requires one unique treatment key and one unique control key
for every checkpoint, dose, and graph replicate; no overlap between treatment
and control key spaces; complete checkpoint and graph-pair coverage; constant
graph provenance within each pair; and finite scores in the unit interval.

## Authenticate an exact accepted raw release

Structural validation is appropriate for a fresh rerun, whose floating-point
outputs and shard hashes may differ slightly across compatible GPU platforms.

If the exact accepted ERM raw release is available, authenticate it read-only
against the pinned release manifest:

```bash
python scripts/run_edge_dose_response_expansion.py validate \
  --preparation erm \
  --graph-root "$GRAPH_ROOT" \
  --catalog-root "$CATALOG_ROOT" \
  --checkpoint-root "$CHECKPOINT_ROOT" \
  --output-root outputs/edge-dose-response-expansion/actual \
  --release-provenance-manifest manifests/edge-dose-response/release-provenance.json
```

This mode recomputes and checks the graph catalogs, environment-lock hashes,
checkpoint shard sets, consolidated outputs, and accepted validation hash. It
does not rewrite the accepted release.
